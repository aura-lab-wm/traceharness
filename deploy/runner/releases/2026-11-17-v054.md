# Runner moved to TraceHarness 0.5.4 — 17 November 2026

The dedicated Fly runner (`traceharness-runner`) now runs TraceHarness **0.5.4** for its control service and all three runtime images. Execution is enabled on release **v26** with the same coverage as before: eight curated tasks and **19 verified task/runtime/model combinations**, each re-verified on the new images. Native-prompt editing for Claude Code and Codex is preserved, with both inventories regenerated for the new images. Exact identities are in [the evidence JSON](2026-11-17-v054-evidence.json).

## What changed

- The control service and the TraceHarness, Claude Code and Codex runtime images were rebuilt from the attested v0.5.4 wheel (recipe change #35). Between 0.5.1 and 0.5.4 the runner's code changed in one place: block prompts are limited by UTF-8 bytes instead of characters.
- Grader inputs were byte-identical, so both grader images were reused unchanged. The Claude Code (2.1.322) and Codex (0.167.1) executables are byte-identical in the new images; the materializer and taxonomy hashes are unchanged. Only the image digests changed, so both native-prompt inventories were re-finalized with the new digests; they differ from the 0.5.1 inventories only in `image_digest` and `inventory_sha256`.

## Verification

- **Native prompts.** For each runtime, six offline captures ran on the VM's gVisor sandbox (original binary, Keep, no-op Replace, marker Replace, single Disable, all-patchable Disable) against a loopback fake API; no provider was contacted. Both comparisons passed and new mechanism receipts were issued.
- **Compatibility.** All 19 combinations hold a receipt from `verify_runtime.py`, with the same caps as the 0.5.1 receipts. Thirteen passed on the first attempt. Six needed a second or third attempt; the eight unsuccessful attempts are kept in the evidence JSON:
  - Two Claude Code attempts were refused by OpenRouter (HTTP 403) because the operator's key had reached its spend limit; both passed once the limit was raised.
  - Five Codex attempts finished with a failing grade or a runtime error: three model attempts whose patch the grader rejected, one stopped at the 20-request cap with a passing patch, and one ended with "Model transport outcome is uncertain". Each combination then passed under the same caps.
  - Reported cost of all attempts, including the member proofs: $2.99.
- **Member flow.** A signed-in member job (Claude Code, native-prompt marker profile, `requests-unicode-length`, $1 cap) succeeded and passed independent grading in 11 requests ($0.41). The replacement was observed in the emitted requests, every artifact hash matched, a hostile Origin was refused, and the transient credential was revoked. A first attempt with a 12-request limit reached that limit with a passing patch and is kept as a failed outcome.
- **Anonymous.** `prove-anon.py` exited 0. An unsigned request to the runner API is refused.

## Deployment

1. **v22 and v23 (execution disabled).** v22 booted the 0.5.4 control on a staging registry with the new digests and no native-prompt bindings, so the boot could not fail on an unbound inventory (the cause of the v18 failure in the 0.5.1 release). v23 switched to the final registry after the captures.
2. **v24 (rollback).** Partway through the compatibility runs the operator's OpenRouter key reached its spend limit, so the runner went back to the v21 image and the 0.5.1 registry with execution enabled.
3. **v25 (disabled) and v26 (enabled).** After the limit was raised, the remaining runs completed on v25; v26 enables execution on `/data/inventory-eight-v2/registry-v054.json`. The 0.5.1 registry and inventories remain on the volume for rollback.
